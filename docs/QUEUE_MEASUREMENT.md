# busy-v1 3건 순차 처리시간 측정

2026-10-17 · TEL-069 · queue-timing.v1. 구현 기준 main4ea904a(PR28 문맥 매칭, PR29 운영 seed 분리 포함). 실제 측정 파일의 build_sha가 해당 실행의 기준이다. 이 문서는 측정 도구와 절차이며 최신 배포의 실제 AI 성능 결과가 아니다.

## 사용 방법

1. B가 운영과 분리한 측정 환경을 준비하고 사용할 busy-v1 운영 seed를 동결한다. 저장소 `app/fixtures/v1/seed_busy.json`은10/16판, `seed_busy_1017.json`은10/17판이다. 각각의 clock_anchor·파일 SHA256·서버 reset manifest hash를 따로 기록하고 서로 다른 판을 같은 실험으로 섞지 않는다. C gold/사례 분류는 모델·실행자 입력에 넣지 않는다. 측정 도구는 초기화·배포를 수행하지 않는다.
2. 관리자 화면의 **3건 순차 처리 → 3건 처리시간 측정**을 연다. 기존 큐가 DONE이면 **새 요청3건 접수**를 먼저 누른다. 진행 중인 큐를 중간부터 측정할 수 없다.
3. 측정자 식별자·seed 파일 SHA256(선택)을 입력하고 실제 AI 여부를 선택한다. 기본은 UNVERIFIED다. REAL은 실행자의 기록일 뿐 실제 과금/호출을 증명하지 않는다. 모델별 실제 호출은 API 로그/원장과 request ID로 대조한다.
4. **다음3건 측정 준비**를 누른다. 이 버튼은 모델/API를 호출하지 않는다. 원문 입력·로그인·초기 조회는 측정에서 제외된다. **3건 함께 접수** HTTP 호출 직전부터 자동 계측한다.
5. 각 요청을 해석→조건 확인·수정→계산→변경안 검토→확정/보류한다. 설명은 READY일 때1회 사용하는 정책으로 고정한다. 추가 호출이나 직접 입력을 쓰면 그대로 기록한다. 앞선 확정은 유지되고 다음 안은 서버의 최신 revision을 사용한다. 측정기가 재시도·확정·보류를 대신 하지 않는다.
6. 세 번째 확정 또는 보류의 성공 응답을 받으면 자동 종료한다. **측정 JSON 저장**, **기록표 CSV 저장**으로 파일을 보관한다. 새로고침/로그아웃/단일 요청 전환/초기화 전에 저장한다. 서버 DB나 localStorage에 측정 기록을 저장하지 않는다. 새 측정은 파일 저장 후 새로고침해 준비한다. 중단은 측정만 멈추며 요청을 취소하지 않는다.

유료 AI 실제 측정은 승인된 모델·예산이 있을 때만 수행한다. 이번 구현 검증은 FakeClient/무료 시험뿐이며 REAL 결과를 만들지 않았다. 신규 설치의 반납일 확인 등 현재 미지원 흐름은 성공으로 바꿔 기록하지 않는다. 지원 기존 업무 변경3건 또는 C가 제공한 사례를 사용하고 실패/미지원/보류도 결과에 남긴다.

## 시간의 정의

`performance.now()` 단조시계로 API 시작부터 응답 본문 수신·JSON 처리 완료까지 잰다. 달력 기준시각은 별도 실제 ISO 시각이며 seed의 clock_anchor와 다르다. AI API 대기는 provider 대기 외에 서버·네트워크·검증/캐시를 포함한다. 계산 API도 solver 외 snapshot·독립검증·저장을 포함한다. 순수 provider latency는 기존 `rentwise.ai latency_ms`/원장으로 따로 확인한다.

| 기록 | 정의 |
|---|---|
| ai_interpret_ms | 큐 해석 API의 응답 대기. 오류·명시 재시도 포함. 저장 해석 재사용이면 실제 모델 호출이 아닐 수 있음 |
| ai_explanation_ms | AI 설명 API 응답 대기. SYSTEM 대체도 포함하며 source와 오류 코드를 별도 보관 |
| solver_ms | 큐 변경안 생성 API 응답 대기. 미해결·재계산도 포함 |
| other_ms | 접수·조건 저장·확정/보류·큐/일정/참조 재조회 등 관찰된 관련 API 대기 |
| human_estimate_ms | 위 API가 진행되지 않은 구간. 조건 읽기·편집·추천값 선택·검토·클릭·유휴 및 렌더 공백을 포함하는 **추정치**, 주의집중시간 실측 아님 |
| total_ms | 접수 시작~마지막 결정 응답의 벽시계 총시간 |
| setup_ms | 접수 시작~첫 요청 활성화. 접수 API는 other에 포함하며 합계에 두 번 더하지 않음 |
| entries[].queue_wait_ms | 접수 시작부터 해당 요청 차례까지. 선행 처리시간을 설명하는 보조값이며 전체 total에 가산하지 않음 |
| entries[].metrics | 해당 요청 차례 시작~결정 응답. 다음 요청은 이전 결정 응답부터 시작하므로 자동 전환 조회도 포함 |

합계는 겹치지 않는 시간구간으로 계산한다. 동시 API가 겹치면 해석→설명→계산→기타 순서로 배정한다. 따라서 각 API 개별 대기시간 합계와 전체 wall-time은 다를 수 있다. `spans`로 요청별 원시 구간/오류/결과상태/완결 여부를 확인한다. 확정 응답보다 늦게 끝난 설명은 전체 경계에서 잘리고 completed=false다. AI 응답을 받기 전에 확정·보류한 경우 DECISION_WITH_PENDING_AI로 비교 제외한다. 접수 setup+각 요청 total=전체 total이며 선행대기는 중복 합산하지 않는다. 총 종료에는 마지막 결정 이후 보드 재조회/안내문 복사가 포함되지 않는다. 기존 사람 포함 전후 측정의 ‘저장 재조회까지’ 지표와 직접 섞지 않는다.

## 결과 판정과 중단

- JSON: build/engine/dataset/clock_anchor/초기revision/계획/직원·장비·고객 규모, 실행자/seed hash/실제AI 여부 기록, 요청ID·계획ID·각 계산 base_revision·확정revision·결과/오류구간을 보관한다. 원문/고객명/키·비밀번호/응답 전체는 내보내지 않는다. CSV는 요청별3행+TOTAL행이며 같은 주요메타데이터를 반복한다. 숫자는 반올림 전 ms, 화면은 초로 표시한다.
- `timing_valid=true`: 관찰 중단 없이3건을 끝냈다는 뜻이다. **3건 확정·정확성·실제 AI·비용 판정이 아니다**. `all_confirmed=true`를 별도로 확인하고 C가 정확성을 독립 판정한다. 실패 호출 후 수동대체로 확정했다면 실패 흔적을 유지한다.
- 탭 숨김(PAGE_HIDDEN), 준비 후 다른 확정으로 초기 revision이 달라짐, 기록되지 않은 계획 복원은 비교 제외 사유를 남긴다. 외부 결정/확정 응답 유실 후 GET으로 종료 상태를 발견하면 시점을 추측하지 않고 ABORTED로 끝낸다. 단순 API 오류는 시간/코드를 남기고 사람이 재시도·보류할 수 있다. 새로고침 후 자동 복원/합산은 하지 않는다.
- FAKE/UNVERIFIED와 REAL 결과를 섞어 AI 속도 평균을 만들지 않는다. 모델/프롬프트/가격 버전은 서버 로그·배포 SHA와 함께 별도 기록한다. GET 성공이나 AI origin만으로 새 모델 호출을 단정하지 않는다.

## 반복 실험과 수동 비교

동일 build·seed·실제 모델·예산·원문3개·순서·설명 정책을 고정하고 매 묶음을 같은 초기 snapshot에서 시작한다. 앞선 확정이 이어져야 하므로 **묶음 내부에서는 reset하지 않는다**. 워밍업은 별도, 본 실험은 최소5묶음부터 원시값·성공/보류/오류 수와 함께 제시한다. 적은 표본으로 P95나 동시 사용자 처리량을 단정하지 않는다. 다른 유형3개를 처리하는 정확성 판단은 C가 맡는다.

수동 비교는 양쪽 동일 시작·종료 경계가 필요하다. 입력 준비 시간은 분리하고 진행자가 사전에 입력하며 실행자는 원문을 미리 보지 않는다. 양쪽에 같은 원문3개·운영자료를 시작 시 공개하고, 같은 변경안 기록/자체확정 기준으로 끝낸다. 플랫폼의3건 시작~최종응답과 수동의3건 시작~최종저장을 비교하되 저장 재조회 포함 여부를 맞춘다. 실패·보류는 별도로 비교하고 품질이 맞는 쌍만 확정시간 개선율을 계산한다. 기존 단건 측정 절차/학습효과·독립판정 원칙도 유지한다.
